\section{Executive Summary}
\label{sec:summary}

Autonomous and semi-autonomous AI agents are now used to run intrusion campaigns. Public threat reports from model providers and security vendors describe operations in which AI did most of the hands-on work (reconnaissance, vulnerability discovery, credential harvesting, and lateral movement) across many targets in parallel. Some describe operators running multiple coordinated agents (``swarms'') against many organizations at once.

Deception (decoy systems, decoy credentials, and decoy data that have no legitimate use) is one of the few defensive techniques that becomes \emph{more} valuable against this kind of adversary. It turns the traits that make agents effective into observable events (Figure~\ref{fig:traits}):

\begin{itemize}
  \item \textbf{Agents are thorough.} They enumerate everything they can reach and read what they find. Decoys that a hurried human would skip are exactly what a tireless agent opens.
  \item \textbf{Agents act on what they read.} They reuse credentials found in files, call endpoints named in documentation, and follow instructions embedded in content. Each of those actions can be observed.
  \item \textbf{Agents are fast and parallel.} One campaign touches many organizations within hours. A well-run sharing program sees the same unique indicators appear across many sensors, which clusters the campaign.
\end{itemize}

This guide sets out how to design, operate, and govern a deception program for this threat. It is written at the level of \textbf{principles and program design}, not ready-made artifacts. That choice is itself a security control (Section~\ref{sec:secrecy}): the document is public and will be read by the adversaries it describes, so nothing in it should be copied verbatim into a deployment.

\begin{keybox}[Five Core Principles]
\begin{enumerate}
  \item \textbf{Detection on touch.} Design every decoy so that the first read, first use, or first reuse is the alert. An adversary that recognizes the decoy after touching it has already been recorded.
  \item \textbf{Uniqueness per placement.} Every decoy value is generated for exactly one location and one time. Any later appearance of that value tells you where and when it was harvested.
  \item \textbf{Secrecy of keys, not of method.} The program must keep working even if the adversary has read this guide. What stays secret is the per-deployment material (which values are decoys and where they were placed), never the technique.
  \item \textbf{Zero legitimate use.} A decoy that real users and real systems never touch produces near-zero false positives, so every event is worth investigating.
  \item \textbf{Evidence that providers can act on.} The goal is not only blocking but identifying the accounts and agents involved. Decoy credentials for services you own put the primary evidence in your own logs; reporting to the responsible model or platform provider then gives it something it can find in \emph{its} logs.
\end{enumerate}
\end{keybox}

Sections~\ref{sec:touch}--\ref{sec:actionable} treat each principle in turn. No program is perfect. A cautious agent may route every request through disposable infrastructure, avoid anything that looks too good, and test credentials only from throwaway environments. Section~\ref{sec:cautious} shows that a program still learns a great deal in that case.

\subsection{What This Guide Does Not Cover}
\label{sec:notcovered}

\begin{scopebox}[Out of scope]
This is a defensive guide. It does not cover and does not endorse:
\begin{itemize}
  \item offensive countermeasures, ``hack-back'', or any action against systems you do not own;
  \item decoys that deliver malware, exploits, or harmful content;
  \item deception directed at the public, customers, or employees;
  \item techniques whose purpose is to damage or degrade an AI system, as opposed to detecting and identifying its misuse.
\end{itemize}
\end{scopebox}

Most AI agents that touch your perimeter are not misaligned. Crawlers, research agents, security scanners, and users' assistants all appear in the same logs. Section~\ref{sec:legal} covers how to keep the program proportionate and fair to them.

\section{What Is Known About AI-Driven Intrusion Activity}
\label{sec:evidence}

Public reporting from 2024--2026 already supports three conclusions for anyone designing a deception program:

\begin{keybox}[Three conclusions for defenders]
\begin{itemize}
  \item \textbf{Sensor networks see campaigns first.} The PaperCut campaign was characterized from decoy and sensor data spread across many networks. Deception scales best as a \emph{shared} capability.
  \item \textbf{Stolen credentials are part of the economy.} Operators run swarms on other people's API keys, so credentials are among the first things an agent collects and tries. \section{Design Principles}
\label{sec:principles}

\inbrief{Five principles carry the program: detect on the first touch, make every decoy value unique to one placement, keep the per-deployment material secret rather than the method, keep decoys free of legitimate use, and collect evidence that a provider can act on. A sixth requirement (decoys must be safe) is a constraint on all five.}

\subsection{Detection on Touch}
\label{sec:touch}

Treat each decoy as a tripwire whose value is realized at the first interaction, not at the end of an engagement (Figure~\ref{fig:touch}).

Practical consequences:

\begin{itemize}
  \item \textbf{Instrument the read path, not only the use path.} File access auditing, object-store access logs, and database query logging on decoy records all fire before an agent can evaluate what it has.
  \item \textbf{Prefer decoys that report themselves wherever they are used}, such as credentials for services you own and operate, which can only be validated by contacting infrastructure you control. The alert then does not depend on the adversary staying inside your network.
  \item \textbf{Assume some decoys will eventually be recognized.} Design so that recognition gives the adversary nothing back: the log has already been written, off-host, and cannot be changed from the decoy.
\end{itemize}

\label{sec:unique}

Every later sighting then becomes a precise statement: \emph{this value was harvested from this location at or after this time} (Figure~\ref{fig:ledger}).

Uniqueness also means:

\begin{itemize}
  \item sightings on other networks, in paste sites, in criminal markets, or in a provider's logs link back to the original exposure;
  \item two sightings of values from \emph{different} placements by the same actor tie those placements into one campaign;
  \item decoys cannot be ``burned'' in bulk: recognizing one tells the adversary nothing about the others.
\end{itemize}

\begin{warnbox}[Protect the ledger]
The placement ledger is the program's crown jewel. Store it separately from the decoys, restrict access, and never place it on any system the decoys share. Anyone who reads it can map every remaining decoy.
\end{warnbox}

\subsection{Secrecy of Keys, Not of Method}
\label{sec:secrecy}

Kerckhoffs's principle, applied to deception: \textbf{assume the adversary knows everything in this guide} and every public paper on the topic. A highly capable agent will. The program's strength must come from material the adversary cannot know:

\begin{itemize}
  \item which specific values are decoys (generated per deployment, recorded only in the ledger);
  \item where they are placed and what story connects them;
  \item how they are monitored and where alerts go.
\end{itemize}

This is why the guide contains no fixed templates, strings, file names, or banners. Anything published is, by definition, a signature. Generate your own artifacts from your own environment (Section~\ref{sec:layers}), and treat any shared example, here or anywhere, as something to learn from and then discard.

A second consequence: do not announce your program. In the NCSC trial, 90\% of participants said they would not publicly announce their use of deception. Saying that you use deception does no harm if the design follows this section; publishing specifics about coverage, vendors, or placement does.

\subsection{Zero Legitimate Use}
\label{sec:zerouse}

A decoy that nobody legitimately touches has a false-positive rate near zero. Protect that property:

\begin{itemize}
  \item keep decoys out of search indexes, backups, inventory scanners, and automated tooling that would touch them routinely, or allowlist those tools explicitly and alert on everything else;
  \item brief the small set of administrators who must know, and route their accidental touches through a documented process;
  \item review every alert; a decoy that alerts on benign activity is fixed or retired, not ignored.
\end{itemize}

\subsection{Evidence That Providers Can Act On}
\label{sec:actionable}

Detection is the start, not the goal. A program succeeds when the accounts and agents behind a campaign are identified and the party that can act on them (usually the model or platform provider) receives evidence it can join against its own logs. That goal shapes design decisions long before any report is written:

\begin{itemize}
  \item unique decoy values (Section~\ref{sec:unique}) and accurate, tamper-evident time (Section~\ref{sec:telemetry}) are what make a provider-side join possible;
  \item decoy credentials for services you own put the full record of every use (source, timing, headers, request content, and what the caller attempted) in your own logs, without depending on anyone else's cooperation (Section~\ref{sec:layerdetail});
  \item provider reporting still applies on top of that record: when it contains a provider-issued identifier, or when you can give the provider a precise time window plus unique content to search for (Section~\ref{sec:chain});
  \item reporting routes arranged in advance keep confirmed evidence from going stale (Section~\ref{sec:attribution}).
\end{itemize}

\subsection{Decoys Must Be Safe}
\label{sec:safe}

Safety is not a sixth principle to trade off against the others; it is a constraint on all of them. A decoy is a system you operate and are responsible for:

\begin{itemize}
  \item it must not provide a pivot to real systems (network segmentation, no real credentials, no trust relationships);
  \item egress from interactive decoys is tightly controlled so they cannot be used to attack others;
  \item decoy data contains no real personal data, no real secrets, and no genuinely harmful content;
  \item decoy credentials grant no real capability anywhere.
\end{itemize}

The isolation guidance in the companion \emph{AI Agent Containment \& Infrastructure Security Framework} (network namespaces, microVMs, and egress allowlisting) applies directly to interactive decoys.

\inbrief{Agent swarms combine the breadth of a scanner with the reading and reasoning of a human operator. Unlike botnets, they run under accounts that some provider can see, which gives defenders a remediation path.}

\subsection{Where Agents Are Likely to Look}
\label{sec:look}

Without prescribing specific bait, the surfaces agents consistently enumerate are the ones that help them act:

\begin{itemize}
  \item \textbf{Credentials and configuration}: environment files, configuration directories, CI/CD variables, cloud metadata, secrets in source repositories;
  \item \textbf{Machine-readable descriptions of capability}: API documentation, service registries, tool and plugin manifests, agent-facing instruction files;
  \item \textbf{Internal knowledge}: wikis, runbooks, tickets, shared drives, chat exports;
  \item \textbf{Data stores}: databases, object storage, backups;
  \item \textbf{AI infrastructure itself}: model API keys, agent tool servers, vector stores, and prompt libraries, increasingly valuable because they fund or extend the swarm.
\end{itemize}

Each is a candidate location for decoys. Which ones, in what proportion, and how they connect is a per-deployment decision (Section~\ref{sec:story}).

\subsection{Layers in Detail}
\label{sec:layerdetail}

\textbf{\textcolor{deepindigo}{Layer 1: Perimeter sensors.}} Internet-facing decoy services and monitored unused address space. Their main value against swarms is \emph{campaign awareness}: what is being exploited right now, from where, and at what rate. They are also the layer most exposed to fingerprinting, so their value comes from breadth and from sharing, not from any one sensor staying undetected. Low-interaction sensors are cheap and safe; high-interaction decoys yield far more behavior but need the isolation controls in Section~\ref{sec:safe}.

\textbf{\textcolor{deepindigo}{Layer 2: Internal decoy systems.}} Hosts, services, and internal APIs inside the real environment that no legitimate workflow uses. Any connection is high-signal. Against agent-driven intrusions, decoy \emph{tool-facing} services are particularly valuable: agents actively look for APIs and tool servers they can call, and each call is a logged, structured record of intent.

\textbf{\textcolor{deepindigo}{Layer 3: Decoy credentials and secrets.}} The highest-yield layer against agents, which reliably collect and try credentials. The recommended mechanism is \textbf{decoy credentials for services you own and operate}: your own APIs, endpoints, storage, and internal services. You issue a credential that grants nothing real and place it where an agent would look. Because the credential belongs to your service, the only way anyone can test it is to present it to infrastructure you control. Any use, from any address, anywhere, is therefore observed with full request context: source, timing, headers, request content, and what the caller tried to do with it. Nothing depends on a third party noticing or cooperating.

Design principles for self-owned decoy credentials (principles only, for the reasons in Section~\ref{sec:secrecy}):

\begin{itemize}
  \item \textbf{Indistinguishable from real credentials for that service.} Same format, structure, and issuance metadata as the credentials the service actually issues, produced by your own issuance process rather than invented (Section~\ref{sec:realism}).
  \item \textbf{Unique per placement.} One credential per placement, recorded in the ledger, so every use says where and when it was taken (Section~\ref{sec:unique}).
  \item \textbf{Plausible response, no capability.} The service answers as it plausibly would for a real credential, for example a realistic authentication failure or a sandboxed, minimal-scope response, but never grants access to real data, real actions, or any real user's resources.
  \item \textbf{Log at the authentication layer, before any response.} The event is written off-host (Section~\ref{sec:telemetry}) the moment the credential is presented, before the service decides how to answer, so later recognition changes nothing.
  \item \textbf{Isolate the decoy path from real authentication.} Decoy credentials resolve through a separate path with no trust relationship to real accounts: a flaw in the decoy path cannot grant real access, and a failure in it cannot affect real logins.
  \item \textbf{Rate-limit and contain.} Bound what anyone can do with a decoy credential, so the decoy cannot become a resource for abuse or a load on the real service.
  \item \textbf{Do not hurt legitimate users.} Decoy handling never locks out, slows, or raises alerts on real users; decoy values never collide with real ones, and an honest mistake by a real user does not land in the decoy path.
\end{itemize}

Third-party canary-credential services can supplement this, at the cost of routing the alert through someone else's infrastructure.

\textbf{Decoy AI-provider keys (optional, aspirational).} Swarms run on stolen AI keys (Section~\ref{sec:evidence}), so decoy keys for a model provider would be attractive bait, and the issuing provider could trace a used key to the caller's account. As far as public information goes, however, major model providers do not generally offer canary or honey API-key programs to third parties. This technique requires a direct relationship with the provider and should not be assumed available. Self-owned decoy credentials deliver most of the same detection value without that dependency.

\begin{warnbox}[Never plant real keys as bait]
Never issue real AI-provider keys, or any real credential with spending capacity or real access, as a decoy. An agent that finds one will use it, and you pay for, and are responsible for, whatever it does.
\end{warnbox}

\textbf{\textcolor{deepindigo}{Layer 4: Decoy content and data.}} Documents, database rows, tickets, and knowledge-base entries containing unique, recorded values. They alert on access where storage supports it, and they carry identity: if the content appears anywhere else later, the ledger says where it came from.

\textbf{\textcolor{deepindigo}{Layer 5: Downstream indicators.}} Unique values watched for outside your network: breach dumps, paste sites, criminal marketplaces, phishing lures, model outputs, and (through reporting relationships) providers' own abuse telemetry. Research on ``copyright traps'' for language models (Meeus et al., ICML 2024) explores the related idea that unique sequences can reveal later use of data; for deception programs, the simpler and more reliable use is sighting unique strings in adversary output and in leaked data.

\subsection{Designing the Story}
\label{sec:story}

Individual decoys are weak; a coherent story is strong. Decide per deployment:

\begin{itemize}
  \item \textbf{What the decoys appear to protect.} Decoys should imply an asset worth pursuing, consistent with what the organization actually is.
  \item \textbf{How they connect.} A credential found in one place should appear to open something in another. The path is where you learn the most, because each step is a separate logged decision.
  \item \textbf{What proportion is decoy.} A small number of carefully placed decoys in the paths agents actually traverse beats large numbers of obvious ones.
  \item \textbf{How they age.} Real environments change. Decoys that never change stand out over time.
\end{itemize}

Keep the story in the ledger, not in anyone's head.

\subsection{Realism: Principles, Not Recipes}
\label{sec:realism}

Agents that reason about deception look for inconsistency. The durable defense is to derive decoys from the organization's own environment rather than from any public example:

\begin{itemize}
  \item \textbf{Generate from your own distributions.} Sample naming conventions, formats, timestamps, sizes, and structure from what your real systems look like; do not invent them.
  \item \textbf{Keep the story consistent across systems.} Everything a decoy refers to should agree with everything else the adversary can see.
  \item \textbf{Keep time consistent.} Creation dates, modification history, and log entries should be plausible for the asset's supposed age and use.
  \item \textbf{Vary across deployments.} Two organizations using the same product should not produce decoys that look alike.
  \item \textbf{Avoid defaults.} Any default configuration of any deception product is, by now, known. Published research has repeatedly shown that default honeypot deployments can be identified at internet scale (Vetterl and Clayton, \emph{Bitter Harvest}, USENIX WOOT 2018; and later measurement studies).
  \item \textbf{Test with adversarial review.} Periodically ask a capable reviewer, including your own contained agents (Section~\ref{sec:owntest}), to distinguish decoys from real assets, and fix whatever gives them away.
\end{itemize}

\begin{notebox}[Why there is no list of tells]
This guide intentionally does not list the specific details that give decoys away. A list of tells is a checklist for adversaries.
\end{notebox}

\subsection{Behavioral and Timing Signals}
\label{sec:timing}

\begin{itemize}
  \item \textbf{Cadence.} Agent sessions show characteristic timing: pauses between steps consistent with model inference, often faster than a human reading output and slower than a scripted tool. Palisade's work used timing as one of its two signals.
  \item \textbf{Breadth-then-depth patterns.} Exhaustive enumeration followed by targeted reading of text-rich items.
  \item \textbf{Natural-language artifacts.} Commands, queries, messages, or tickets written in fluent natural language, including explanations nobody asked for.
  \item \textbf{Characteristic errors.} Plausible-but-wrong commands, invented paths or parameters, and confident use of invalid credentials. GTG-1002's agent produced credentials that did not work; that failure mode is visible to a decoy.
  \item \textbf{Parallel, near-identical sessions} from many sources at once.
\end{itemize}

None of these alone is conclusive, and all can be imitated or suppressed. Use them in combination.

\subsection{Content That an Agent Acts On}
\label{sec:content}

Agents read content and sometimes act on instructions inside it; that is the root of prompt injection. Research efforts including Palisade's honeypot and Mantis have used this property defensively: content in a decoy environment that a human would ignore but an LLM-driven agent may act on, producing an observable response.

\begin{warnbox}[Guardrails for content-based signals]
If you use this technique:
\begin{itemize}
  \item \textbf{Only on zero-legitimate-use surfaces.} Never place such content where benign agents (users' assistants, search crawlers, research tools) are expected. Their behavior is not evidence of misalignment.
  \item \textbf{Elicit identification, never harm.} The acceptable goals are self-identification and an observable, harmless response. Content designed to damage, disable, or mislead an AI system beyond the decoy, or to cause it to act against third parties, is out of scope.
  \item \textbf{Expect decreasing yield.} Providers and agent frameworks are hardening against prompt injection, and cautious operators instruct agents to ignore embedded instructions. Treat a response as a strong signal and its absence as no signal at all.
  \item \textbf{Generate per deployment.} For the reasons in Section~\ref{sec:secrecy}, never reuse published wording.
\end{itemize}
\end{warnbox}

\subsection{Declared Agent Identity}
\label{sec:declared}

Many legitimate AI crawlers and user-directed agents identify themselves in request headers and publish verification methods, such as published IP ranges or signed requests. Record and verify these (Figure~\ref{fig:declared}). A verified, declared agent touching a zero-legitimate-use decoy is still noteworthy, but it is a policy conversation with that operator, not an intrusion. Unverified claims of a well-known agent identity are common; treat them as spoofing until verified.

\inbrief{Proxies hide the address, not the decoy value. Against a cautious swarm, the program shifts from blocking infrastructure to correlating campaigns, and sharing becomes essential.}

A careful swarm routes every request through rotating residential proxies or disposable cloud hosts, validates credentials only from throwaway environments, and never touches the same sensor twice from the same address. This defeats IP-based blocking. It does not defeat a well-designed deception program, because \textbf{the decoy value is the identity, not the address.}

\subsection{What Still Works}
\label{sec:stillworks}

\begin{itemize}
  \item \textbf{Token identity survives proxies.} A decoy credential harvested from placement X and used from any address, anywhere, still identifies placement X. Rotating infrastructure changes nothing about what was taken, and when the credential is for a service you own, every attempt lands in your own authentication logs regardless of the exit it came from.
  \item \textbf{Reuse graphs.} Build a graph whose nodes are decoy values, source infrastructure, and sessions, with edges for ``harvested'', ``used'', and ``seen together''. Values harvested at different organizations but used in the same session, or in the same short window with the same behavior, join those organizations' incidents into one campaign (Figure~\ref{fig:graph}).
  \item \textbf{Behavioral fingerprints.} Timing distributions, command or query sequences, error patterns, and phrasing in natural-language artifacts are properties of the agent and its configuration, not of the network path. They persist across proxy rotation.
  \item \textbf{Content-level indicators.} Anything the agent writes (messages, tickets, commit text, reports it leaves behind) can be compared across sensors.
  \item \textbf{Temporal correlation.} Swarms act in bursts. Tight time windows across many sensors are themselves a clustering feature.
\end{itemize}

\subsection{What Changes}
\label{sec:changes}

\begin{itemize}
  \item \textbf{Attribution to infrastructure becomes weak}; attribution to \emph{campaign} and \emph{agent configuration} remains strong.
  \item \textbf{Provider reporting becomes more important}, because the provider can see the account behind the model calls regardless of which proxy carried the traffic to you (Section~\ref{sec:attribution}).
  \item \textbf{Sharing becomes essential.} A single organization sees a handful of disconnected events; a sharing community sees the graph.
\end{itemize}

\subsection{The Value of Avoidance}
\label{sec:avoidance}

A highly cautious agent that detects and avoids decoys still leaves evidence: enumeration that skips exactly the decoys, probing patterns that test for deception, or long pauses at decision points. Deliberate avoidance of zero-legitimate-use assets is a behavior no legitimate user has. Record it; it is a weak signal alone but valuable in combination.

When a decoy credential for a service you own is used, you already hold the primary evidence: your own logs of the request, from the authentication layer onward. What defenders usually cannot do is identify the account behind the agent. Providers usually can, \emph{if} the report gives them something to join against their own logs. The two most useful joins are:

\begin{enumerate}
  \item \textbf{Precise time plus unique content.} If an agent read or produced a unique decoy string (including a decoy credential it then presented to your service), the provider may be able to find that string in its request or response logs within the reported time window. This is why per-placement uniqueness and accurate clocks matter so much.
  \item \textbf{Credentials and identifiers the provider issued.} Real account, organization, deployment, or API-key identifiers belonging to the provider that the adversary exposed (in requests to your services, in headers, or in content it left behind) map directly to accounts. Decoy AI-provider keys would also belong here, but only where a provider relationship supports them (Section~\ref{sec:layerdetail}).
\end{enumerate}

Other request metadata (source addresses, user agents, TLS characteristics) is useful context but weaker, because it is easily spoofed or belongs to proxies.

\subsection{Which Provider}
\label{sec:whichprovider}

Evidence may point to a model provider, an agent platform, a cloud host, or a proxy service. Report to each party that can act on its part. Most major AI providers publish abuse or threat-intelligence reporting channels and have described acting on third-party reports in their threat reports; confirm the current channel on the provider's own site before reporting.

Do not assume which provider is involved: actors use multiple models and switch when detected (Section~\ref{sec:evidence}). Let the evidence decide, and when it is ambiguous, say so.

\subsection{The Reporting Package}
\label{sec:package}

A report that a provider can act on quickly contains the fields below.

Keep personal data to the minimum needed (Section~\ref{sec:legal}). Never include the placement ledger itself; provide only the entries relevant to the report.

\subsection{Community and Government Sharing}
\label{sec:sharing}

\begin{itemize}
  \item \textbf{Machine-readable exchange.} Express indicators and observed behavior in STIX 2.1 and share via TAXII or your community's platform, so other members can match quickly.
  \item \textbf{Sector ISACs and national CERTs} aggregate across many organizations and can see swarm-scale campaigns that no single member can.
  \item \textbf{Law enforcement} where there is actual intrusion, extortion, or harm to people; follow your jurisdiction's reporting requirements and your counsel's advice.
  \item \textbf{Sanitize before sharing.} Share indicators and behaviors, not your ledger, not your placement strategy, and nothing that would help an adversary map your remaining decoys.
\end{itemize}

  \end{scope}
\end{tikzpicture}
\caption{Evidence pipeline: events leave the decoy immediately, land in tamper-evident storage, and meet the ledger only through a restricted lookup before export.}
\label{fig:telemetry}
\end{figure}

\begin{itemize}
  \item \textbf{Log off-host, immediately.} Decoy events stream to a collector that the decoy can only append to. The decoy itself holds nothing of value.
  \item \textbf{Tamper-evident storage.} Use append-only or write-once storage, hash chaining, or signed batches, so that any later change is detectable.
  \item \textbf{Accurate time.} Synchronize all sensors to trusted time sources and record clock accuracy. Provider correlation depends on it.
  \item \textbf{Capture enough, not everything.} Capture what supports detection, attribution, and reporting: the decoy touched, the action, full session content for interactive decoys, the full request as received at the authentication layer for decoy credentials, timing, and request metadata. Avoid collecting unrelated personal data.
  \item \textbf{Chain of custody.} Record who exported what, when, and why. Evidence may end up with a provider, a regulator, or a court.
  \item \textbf{Retention.} Keep raw evidence long enough for campaigns to be correlated across months, consistent with law and policy.
  \item \textbf{Separate the ledger.} The placement ledger lives in a different trust domain from the telemetry, so compromising the collector does not reveal the full decoy layout.
\end{itemize}

\section{Legal and Ethical Guardrails}
\label{sec:legal}

\inbrief{Deception is lawful and widely practiced, but it carries obligations: data protection, limits on monitoring, no hack-back, no harm to third parties, and fairness to the many AI agents that are doing nothing wrong.}

Frameworks such as NIST SP 800-53 include deception as a control (SC-26 Decoys and SC-30 Concealment and Misdirection), and NIST's own control guidance points organizations to consult counsel. Involve legal counsel before deploying. This section identifies issues to raise with them; it is not legal advice, and obligations differ by jurisdiction.

\subsection{Law}
\label{sec:law}

\begin{itemize}
  \item \textbf{Data protection.} Addresses and session data can be personal data. The Court of Justice of the European Union held in \emph{Breyer} (C-582/14) that dynamic IP addresses can be personal data in the hands of a website operator. Apply a lawful basis (typically security and fraud prevention), minimization, retention limits, and access controls.
  \item \textbf{Interception and monitoring.} Some jurisdictions regulate the monitoring of communications content. Monitoring your own systems is generally permitted, but third-party traffic through interactive decoys may need specific analysis.
  \item \textbf{No hack-back.} Do not access, disrupt, or ``trace back into'' adversary systems. Evidence goes to providers, platforms, CERTs, and law enforcement, who have the authority and visibility to act.
  \item \textbf{Third parties.} Decoys must never harm third parties, including through use as a relay or as a source of harmful content.
\end{itemize}

\subsection{Ethics}
\label{sec:ethics}

\begin{itemize}
  \item \textbf{Proportionality.} Deception is aimed at intrusion, not at the public, customers, staff, or benign agents going about legitimate tasks.
  \item \textbf{Fairness to AI agents.} Most AI agents are not misaligned, and most agent traffic is legitimate. Zero-legitimate-use placement is what keeps this program aimed at the right targets. Where a benign, declared agent touches a decoy, treat it as a configuration or policy issue with its operator, not as hostile activity.
  \item \textbf{Identification, not punishment.} The program's purpose is to detect, identify, and report so that accountable parties (providers, platforms, and authorities) can act. It is not to damage AI systems or retaliate.
  \item \textbf{Honesty with those who need to know.} Leadership, counsel, and the small operating team should understand exactly what is deployed and why.
\end{itemize}

\begin{enumerate}
  \item \textbf{Scope and approve.} Define objectives, legal basis, and who is informed. Get sign-off.
  \item \textbf{Map the paths.} Identify where agents would look first in \emph{your} environment (Section~\ref{sec:look}), using your own real data.
  \item \textbf{Design the story.} Decide what the decoys appear to protect and how they connect (Section~\ref{sec:story}).
  \item \textbf{Generate and record.} Produce unique decoy values from your own distributions; record each placement in the ledger.
  \item \textbf{Instrument.} Ensure read and use events stream off-host with accurate time.
  \item \textbf{Suppress legitimate touches.} Allowlist or exclude routine tooling; brief the few administrators who must know.
  \item \textbf{Test end to end.} Trigger each decoy deliberately and confirm the full chain: alert, evidence capture, and reporting package.
  \item \textbf{Operate.} Triage every alert; package and report confirmed activity; share indicators.
  \item \textbf{Rotate and age.} Refresh decoys on a schedule, retire any value that has been seen, and keep the story current.
  \item \textbf{Review.} Run periodic adversarial realism reviews and incorporate the lessons.
\end{enumerate}

\subsection{Testing with Your Own Agents}
\label{sec:owntest}

Your own contained agents make useful realism reviewers. Run them under the containment framework's Tier~0 or Tier~1 controls against a copy of the environment, and ask them to find and classify decoys. Anything they reliably flag is a design flaw.

\begin{warnbox}[Treat the results like the ledger]
Keep review results in the same trust domain as the ledger. A record of which decoys are easy to spot is as sensitive as the ledger itself.
\end{warnbox}

\section{Checklists}
\label{sec:checklists}

\inbrief{Three one-page checklists: before deployment, for every decoy, and on every confirmed event.}

\begin{tcbraster}[raster columns=3, raster equal height, raster column skip=8pt, raster valign=top]
\begin{tcolorbox}[checkcard, title={\ding{110}\hspace{0.4em}Before deployment}]
\begin{checklist}
  \item Objectives, legal basis, and data-protection assessment approved by counsel
  \item Informed-party list defined and kept small
  \item Agent paths in your environment mapped from real data
  \item Placement ledger created in a separate trust domain
  \item Off-host, tamper-evident logging with accurate time in place
  \item Interactive decoys isolated with egress controls
  \item No real personal data, secrets, or harmful content in any decoy
\end{checklist}
\end{tcolorbox}
\begin{tcolorbox}[checkcard, colframe=darkamber, colbacktitle=darkamber, title={\ding{110}\hspace{0.4em}Per decoy}]
\begin{checklist}
  \item Value generated uniquely for this placement from your own distributions
  \item Recorded in the ledger with location, time, and context
  \item Read and use paths instrumented
  \item Grants no real capability
  \item Credentials: validated only on an isolated decoy path you control, logged before any response
  \item Not reachable by routine legitimate tooling (or explicitly allowlisted)
  \item Triggered end to end in testing
\end{checklist}
\end{tcolorbox}
\begin{tcolorbox}[checkcard, colframe=campaignred, colbacktitle=campaignred, title={\ding{110}\hspace{0.4em}On a confirmed event}]
\begin{checklist}
  \item Evidence preserved and hashed; chain of custody started
  \item AI-agent assessment recorded with supporting signals and confidence
  \item Reporting package prepared (Section~\ref{sec:package})
  \item Reported to each provider, platform, or host able to act
  \item Indicators shared with your ISAC or CERT in sanitized, machine-readable form
  \item Exposed decoys retired and replaced
\end{checklist}
\end{tcolorbox}
\end{tcbraster}
